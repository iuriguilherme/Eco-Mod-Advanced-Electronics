Drone Dock UI — palette, baseline, and redesign options

Advanced Electronics mod · 2026-07-31 · branch probe/ui-vocabulary
Companion to docs/solutions/design-patterns/vertical-stack-only-ui-design.md and docs/solutions/runtime-errors/autogen-template-binding-contract.md.

This mockup obeys the target's layout primitives. That is the whole point of it. A previous HTML preview of this panel drew Previous/Next side by side; Eco cannot do that, the buttons shipped stacked, and the verdict was "you tricked me — those buttons are still vertical and not horizontal like the preview, lol." Every element below is drawn at its measured size and in its real position. Nothing here uses a capability the client has not been observed to have.

How these numbers were measured

Pixel measurements taken from live client screenshots at .references/Screenshots/14/ (pre-rework Survey tab, 1009×625) and .references/Screenshots/19/ (UI Showcase probe, 987×708), normalised to the panel content box. The showcase component that produced them is EcoServerMod/AdvancedElectronics/UIShowcaseComponent.cs — currently detached at DroneDock.cs:87, one commented line from returning.

1 · Ground rules

Verified primitives. A mockup that breaks one of these is worthless, because it will be approved and then cannot be built.

RuleStatusEvidence
One element per row, in member declaration order. verified Every deployed build. Reading order is declaration order.
Most templates render as a two-column row — label left, control right. A few go full width. verified Showcase probe. Corrects this doc set's original "full-width only" claim.
Panel height is the budget, ~605 px of content before it scrolls. verified Screenshot 14 and 19 both show the panel clipping and a scrollbar appearing.
A dynamically sized list does not render from a mod component. blocked Seven builds. Table/ButtonGrid bound to a collection produce an empty container or crash the window. Root cause is a client type-reconstruction gap (View.cs:114).
Therefore N controls means a fixed pool of compile-time RPC methods. verified The pool is gated per position by a [SyncToView] bool + VisibilityParam.
An editable member persists but does not refresh on screen unless the setter explicitly raises PropertyChanged. verified A/B in one deploy, two adjacent Int32 members. Needs an explicit backing field — an auto-property gives no setter body to push from. Per-member cost.
An editable template with an unreachable setter kills the server for every player. hazard InvalidOperationException: Missing RPC call Set<Prop>. Not visible until someone clicks.
A known template bound to a mismatched value shape also kills the server — merely hovering was enough. hazard Range on a float: Could not finding matching RPC signature for method: SetT_Range.
An unknown template name is safe — logged and skipped. verified View.cs:356. This is the only crash-safety guarantee, and it is narrower than it sounds.

The number that drives everything

standard two-column row 22 px
one line of StringDisplay 18 px
GeneralHeader 34 px
LongString / StringLargeInput ~60 px
BigButton 70 px
StringPlaque 110 px
BigButton is the panel's commit control, and the dock uses it as a list primitive. It is the OK button at the bottom of a screen: fixed size, not groupable horizontally, designed to appear once. Every property that makes it a good commit button makes it a bad repeated element.

The measurement is the symptom, not the diagnosis. One renders ~120 px wide, ~70 px tall, centred, with roughly 400 px of dead panel on each side — exactly what a control meant to sit alone at the bottom of a panel would do. The Areas tab's six assign buttons are 420 px of a 605 px viewport, 69% of everything the player sees without scrolling.

The recorded lesson was "vertical buttons are a terrible design", and the prior rework answered it by using fewer buttons. The sharper reading: buttons are fine, and this one is being used against its purpose. The vocabulary already has controls built for repetition — Boolean for a per-object toggle, Int32 for a cursor — and they cost 22 px because that is what a list element is supposed to cost.

✎ ◉ BigButton, at true size and position
Manage Areas on Map
Assign Area 1

Three BigButtons = 210 px = 9.5 standard rows, and roughly 66% of the panel width is dead in every one of them. It is the only way to expose an [RPC] action today — which is the trap: because it is the only button, it gets reached for whenever something needs clicking, including the many things that are not commits. The redesign options below all convert repeated actions into state edits on repeatable controls, and keep BigButton for the one action that really is a commit.

4 · Untested leads from the SLG wiki

Read 2026-07-31 from Eco.wiki/UI-System.md and Eco.wiki/Fast-UI-extensions.md (task #34). Everything in this section is a lead. None of it has been observed working from a mod component tab. It is here so the options below can be judged against what might become possible, and so nobody re-derives it.

Lead 1 — [Eco] is a composite and it decomposes.
Server/Eco.Shared/Networking/EcoAttributes.cs:17-27 documents it as Serialized + SyncToView + AutoRPC + AutoGen + property scanning + explanation. Our binding contract treats it as an atom. [Serialized, SyncToView, Autogen] without AutoRPC should generate no setter RPC — which would make LongString and StringDescription genuinely read-only instead of a crash waiting for a keystroke. source-verified, client effect untested
Lead 2 — an entire attribute family we never probed. Server/Eco.Core/Controller/AutoGenViews.cs:105-121. Zero mentions across docs/ and EcoServerMod/.
[Sort(float)]Would break "declaration order is reading order." If it works from a mod tab, layout stops being coupled to source order.
[PropReadOnly]Vanilla: PluginModulesComponent.cs:96, PlotsComponent.cs:55 — both on inventory refs with private set. Proven as "no setter", not as "render text non-editably". Different claim.
[LargeUI]Vanilla: [Eco, LargeUI] public string Speech (ElectionActions.cs:160). A multi-line text surface without LongString's crash family.
[OwnerReadOnly] [GuestEditable] [GuestHidden] [OwnerHidden]Per-viewer gating, versus our all-or-nothing VisibilityParam bool. Would let the owner see assignment controls and visitors see only findings.
[Locked] [AdminEdtiableOnly] [Advanced] [HideDescription] [AllowCopyPaste] [DynamicTitle]Edit gating and presentation. [DynamicTitle] names a property to read a label from — the fixed-label problem below.
attributes and vanilla usages verified; behaviour from a mod tab untested
Lead 3 — View_<name> auto-glue could remove the stack constraint entirely.
A hand-built Unity prefab whose child GameObjects are named View_PropertyName binds to view properties with no glue code (ViewExtensions.AutoSetupUI). The wiki's own screenshot shows vanilla's law UI doing this under a horizontal layout group. We already ship a .unity3d bundle. Whether a mod can register into the client's UIPrefabs.ViewUIPrefabs list is unknown.

If it can: the vertical stack is not a law of modding, it is a consequence of using autogen, and every row-budget rule in this document becomes optional. entirely untested — highest upside, highest uncertainty
Negative result — Fast-UI-extensions.md has nothing for us. It is client-side Unity performance work (FastLayout, FastLayoutElement, FastImage) for hierarchies of 1000+ objects, such as inventories. Task #34's premise about that page was wrong. One line matters only if Lead 3 is pursued: convert FastLayout to a regular LayoutGroup when hosting AutoGen prefabs on a container.

5 · Redesign options

All three are buildable today, from proven templates only, with no dependency on section 4. Each is drawn at measured geometry. Judge the shape and the budget; ignore exact wording.

Option A — steppers replace cursors

The minimum change with the largest measured effect. A Int32 stepper is a two-button cursor in one unit; Prev/Next as BigButtons is the same job for 6.4 units. Applies to both tabs independently, and does not touch any product decision.

Results: 306 → 192 px. Prev/Next (140) becomes one stepper (22). The "Viewing" line becomes a String two-column row, so the area name and its state read as one fact instead of a centred sentence — and nothing now separates the cursor from the findings.

Cost of A

  • Every stepper needs the explicit backing field + PropertyChanged pattern, or the number will not move on screen when clicked. Per-member cost, already proven.
  • Range(1, N) must be a constant at compile time. If Range cannot be driven by area count, the stepper's ceiling is fixed the same way the button pool was — the one thing in A that needs verifying before building.
  • A stepper is a weaker affordance than a labelled button. The echo row exists to compensate; if it does not refresh live, the control is worse than what it replaced.

Option B — checkbox roster

Keeps the recorded principle "one control per object, not per operation", and pays 1 unit for it instead of 3.2. Each area gets a Boolean row; checking one assigns it and unchecks the rest. No commit button, no cursor, no indirection between the list and the control — the list is the control.

Areas: 652 → 244 px, and the separate text list disappears — its content moved into the checkbox labels, so one element does the work of two. Sixty percent of the panel is free.

The load-bearing unknown in B: can a row label be driven at runtime? Observed behaviour is that a member renders with its member name, humanised (T_Boolean → "T_Boolean"). If the label is fixed at compile time, B's rows read "Area 1", "Area 2"… and the list must come back as a separate StringDisplay — which costs its 162 px back and lands at ~406 px, still well inside budget but no longer the clean win drawn above.

Two candidate escapes, both from section 4 and both untested: [DynamicTitle("PropertyName")] names another property to read the label from, and [LocDescription] / Description may already override the humanised name. This is the single cheapest probe in the whole document and it decides between B-clean and B-degraded.

Cost of B

  • Still a fixed pool — six Boolean members, same cap as six RPCs. B does not remove the ceiling, it makes each rung cheap. A only removes the ceiling if Range can be dynamic.
  • Radio semantics on checkboxes: checking area 3 must silently uncheck area 2, and all six must push PropertyChanged on every change or the client shows two ticked boxes.
  • Unassigning means unchecking the ticked box — same toggle affordance as today, preserved.

Option C — one merged tab

A and B both free more than half a panel. If that space exists on both tabs, the second tab stops paying for itself: the split was made to halve two over-long panels, and neither is over-long any more. One panel means no tab switch between "which area" and "what did it find".

C is also the option whose row budget is most sensitive to area count: at eight areas the findings block starts crossing the fold.

Decided

Option C — the merged tab. Requirements are in docs/plans/2026-07-31-001-feat-merged-survey-tab-plan.md. Also settled there: placed docks are allowed to break (no migration until the mod has worlds worth preserving), and the control pool stays at six — the row-cost argument for raising it holds, but the workflow that sized it has not changed.

Still open, and answerable only from a live deploy: whether a row label can be set at runtime (decides whether B's checkboxes carry area names or read "Area 3"), and whether a numeric range bound can be non-constant. Section 4's [Sort] and [PropReadOnly] are one attribute each and would ride along in the same restart.
