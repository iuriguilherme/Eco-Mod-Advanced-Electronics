Grounding Context

Codebase context. Unity 6000.3.19f1 + HDRP 17.3.0 Eco ModKit client project — a fresh scaffold with zero custom mod content. The client produces visual assets only (prefabs, icons, block meshes); a matching server-side C# mod must be authored separately, and objects match by exact name. Scene structure requires four roots (Objects / Items / Emoji / BlockSets); export happens via the Eco Tools > Mod Kit menu into AssetBundles/.

  • WorldObject client surface (42 evidence entries): server-synced enabled/operating/using state events; custom bool/string/float state arrays with change events; animator-driven states; network-driven movement only — no client locomotion or vehicle system exists; shader tweens, particle/audio hooks, attachment points, occupancy, pickup predicate.
  • Block sets (20 sections): BlockSet ScriptableObjects, 26-offset neighbor-rule mesh variation (CustomBuilder/OffsetCondition), mesh alternates via noise, 3-level LOD groups, weighted/rule prefab builders, per-block Effects[] hooks, name-based server mapping.
  • Pipeline (12 sections): documented item/world-object/emoji/block-set flows, 64×64 icon template, per-scene bundle builds with lowercased names, CleanName(prefab.name) + "Object" name transformation — silent-failure name contract with the server.
  • External research (value: high): Eco prior art — Auto Mine, Easy Mining, BetterMining (community expects automation gated through the skill-point economy via Configs/), CoFH's small-mods norm, Lara's World Generator precedent, vanilla Mining level-6 partial-automation perks, pragmatic community sentiment. Vanilla chain: ore → Arrastra → Rocker Box → concentrate + wet tailings, with tailings as the pollution gate on heavy extraction. Adjacent patterns: Mekanism yield chains, BuildCraft power-throttled quarry, PneumaticCraft programmable drones, Vintage Story probabilistic prospecting, Factorio bot economics.
  • Past learnings: none — no docs/solutions/ in this repo yet.

1.

Dock-centric drone architecture ("drone-in-a-box")

drone-automation Confidence 85% Complexity: Medium
Description
Make the stationary Drone Dock the gameplay anchor: a craftable WorldObject holding all player interaction (fueling, cargo, orders, repair) through the fully supported state/animator/interactable surface, with hatch-open / launch / land animation states. The flying drone itself is a lightweight, server-pathed SyncPhysics visual the dock dispatches on sorties — the server updates its position each tick, and the client sells agile flight (banking, tilt, hover wobble) through Animator blend trees driven by FloatStates mapped from velocity deltas. First step is a five-minute feasibility prototype: a server mod moves one prefab in a circle.
Basis
direct: "No documented vehicle/locomotion: … no dedicated vehicle controller or waypoint system visible in modkit. Movement appears server-driven only" (WorldObject evidence dossier); SyncPos verified at SyncPhysics.cs:24, kinematic fallback beyond 25m at SyncPhysics.cs:38. external: the real inspection-drone industry (DJI Dock, Percepto) converged on "drone-in-a-box" because unattended free flight is the hard part.
Rationale
This resolves the mod's single hardest technical risk — the ModKit exposes no client locomotion system — by converting the platform limitation into the design. The dock uses only stock, verified client hooks; drone movement becomes a server-mod problem (fully in scope), and the 25m physics-ignore distance acts as free LOD for distant drones. Every prefab, recipe, and server class depends on which way this architectural fork goes, so it should be settled first.
Downsides
Server-driven flight fidelity is unproven until the prototype runs; fast drones may look teleport-y under the snap-distance rule. Dock-centric design constrains "follow my drone around" fantasies — the drone is a visual of a job, not a controllable vehicle.
2.

Shippable v0.1: AE-Ores first, with a name-contract validator

client-pipeline Confidence 90% Complexity: Low
Description
Structure the project as three scenes → three bundles with matching server sub-mods: AE-Ores (blocks + worldgen), AE-Electronics (skill, tables, components), AE-Drones (depends on both) — and ship AE-Ores alone first. The v0.1 art plan is deliberately zero-new-mesh: new ores are new Block definitions with new HDRP emissive materials on reused meshes, icons via the documented 64×64 sprite-swap template. Offer retrofit distribution — deterministic, coordinate-seeded enrichment of existing stone — so live servers can install without a world reset. Week one also builds a small editor "design-rule check": export every prefab/Block/item name to a manifest and diff it against server-mod class names before each bundle build, failing loudly.
Basis
direct: "Build Current Bundle" requires a single open scene and lowercases bundle names (ModKitTools.cs:95-152); Block.Material/Materials[] are per-block data; cleanName = CleanName(prefab.name) + "Object" verified at WorldObjectSetup.cs:78. external: the CoFH/EcoMods norm of small focused mods; Lara's World Generator shows worldgen edits apply only to newly generated worlds.
Rationale
This changes what happens next week. The build tooling already enforces scene-per-bundle, so modularity is nearly free now and expensive after assets tangle into one scene. Ores-only validates the worldgen path, the name pipeline, and community reception months before any drone exists; materials-first art gets the loop testable before modeling starts; and the name validator kills the project's most likely bug class (silent name mismatch across two disconnected repos) while the object count is still near zero.
Downsides
Three bundles mean three server sub-mods and more release coordination. Retrofit enrichment is server-side work with no client evidence — treat it as a server-design commitment. Recolored vanilla meshes risk a "reskin" first impression.
3.

Geology that plays: graded, halo-wrapped, luminous ores

worldgen-ores Confidence 80% Complexity: Medium
Description
One coherent ore identity built from three verified block-system mechanisms. (a) Alteration halos: new ores spawn as vertical pegmatite-style veins wrapped in visually distinct "altered stone" halo blocks, with the 26-offset CustomBuilder rules streaking halo meshes toward adjacent ore — terrain itself teaches players to read geology. (b) Cutoff grades: each ore exists in low/mid/high-grade block variants (mesh alternates + noise); hand miners rationally skip low grade, drones happily chew it — at 3–5× tailings per ingot, so the pollution check on automation emerges from geology rather than an arbitrary penalty. (c) Sensory signal: as tech-tier minerals, the ores carry a faint emissive shimmer and particle hum via per-block Effects[], so a perceptive caver can find them by eye — drones amplify detection, they never monopolize it.
Basis
direct: 26-offset OffsetCondition/BlockRule system and meshAlternates "variations via noise" (block-set dossier); Effects[]/EffectNames[] verified at Block.cs:59-60. external: hydrothermal alteration halos are how real prospectors vector to veins; cutoff-grade economics is standard mine planning; Vintage Story shows probabilistic/readable prospecting preserves exploration under automation.
Rationale
This answers the design question every automation mod faces — "doesn't this trivialize exploration?" — structurally, with zero special-case balance code: humans read halos and shimmer, drones read anomalies and eat low-grade rock at a tailings premium. It also uses the block-rule engine, the most powerful and least-used client capability found in the evidence, for gameplay signaling rather than cosmetics.
Downsides
Grade variants roughly triple the ore-block authoring surface (mitigate with a shared vein-rule/LOD template — see rejection table, carried into planning). Worldgen vein shapes are server-side; the client evidence only proves the rendering half. Emissive ore may read as "magic crystal" without careful art direction.
4.

Closed-loop automation economy: drones manufacture labor

recipes-processing Confidence 70% Complexity: High
Description
A single design rule with three legs, ensuring automation adds jobs and liabilities to Eco's economy instead of deleting them. (a) Rubble, never ore: drones return Unsorted Rubble, a bulk intermediate requiring a new Electrostatic Separator before entering the vanilla Arrastra → Rocker Box → tailings chain — mining clicks are automated away, but sorting, hauling, power, and tailings management jobs are created. (b) Depreciation and e-waste: drones consume durability per sortie; worn drones visibly smoke (stock MaintenanceComponent VFX anchor) and fail into E-Waste, whose recycling recovers metals at high grade while concentrating toxic leachate — a second pollution vector and a recurring income stream for the specialty. (c) Remediation as product: the same specialty sells automated tailings remediation (processing wet tailings toward inert soil over time, visualized with shader tweens) — cleanup becomes gameplay, not an afterthought.
Basis
direct: smokePosition ("Position where Smoke and Sparks effects will appear") verified at MaintenanceComponent.cs:8-9; TweenColor()/TweenFloat() shader hooks in the WorldObject dossier. external: vanilla tailings are the game's gate on heavy extraction; e-waste holds ~40–100× the gold grade of mined ore (urban-mining economics); EVE Online's ship-loss economy is the canonical proof that depreciation sustains player-driven demand.
Rationale
The number-one social failure mode for an auto-mining mod on a multiplayer server is making miners obsolete and bypassing the pollution loop that defines Eco. This closes both at the design level. Caveat from verification: the mechanics here are almost entirely server-mod territory — the client repo contributes only the VFX hooks — so treat this as the server-design brief that accompanies the client work, not a client deliverable.
Downsides
Highest server-side implementation surface of any survivor (new items, tables, durability system, remediation ticks). Extra processing steps risk tedium if tuned wrong — the friction must land on decisions, not clicks.
5.

Semiconductor purity ladder as the processing spine

recipes-processing Confidence 75% Complexity: High
Description
Copy the historical silicon chain as the recipe backbone: metallurgical-grade (cheap, arc-furnace) → polysilicon (energy-hungry, toxic chlorosilane-style byproduct) → monocrystal (slow, low yield). Each drone tier and circuit component demands a higher purity grade of the new ores; each purification stage needs a new table (Reduction Furnace → Purification Column → Crystal Puller), costs disproportionately more power, and emits its own byproduct that plugs into the tailings/pollution system. Advanced Electronics talents reduce yield loss ("clean-room protocols").
Basis
external: the real Siemens-process / Czochralski purity chain — an existing, coherent three-stage escalation of energy, equipment, and waste; the research digest's core constraint that automated systems should plug into, not bypass, tailings/pollution — which this chain does at every stage.
Rationale
It gives "Advanced Electronics" a thematic backbone that isn't just "circuits need copper": purity-as-progression escalates input quality rather than Mekanism-style output multiplication — truer to electronics and a fresher balance lever. It also determines the count and identity of new crafting tables and intermediates: the largest chunk of both server code and client prefab work, which is why it deserves a deliberate decision.
Downsides
Three new tables plus intermediates is a lot of content before the loop is provable; risks over-lengthening the path to the first drone (consider gating only higher tiers behind the ladder). Recipe/skill design is entirely server-side.
6.

Autonomy-graded specialty with XP you can't grind by hand

skill-progression Confidence 70% Complexity: Medium
Description
Structure the specialty's levels as autonomy grades, borrowed from SAE driving-automation levels and FAA drone-pilot certification: level 1 = manual dispatch per sortie, player collects output; mid levels = supervised autonomy within a bounded area; top level = full autonomy with self-refueling from dock storage. Each level is a felt behavior change, not a +% modifier. XP wires to the stock OnEnableOperating/OnDisableOperating events — accruing from automation running (uptime, closed loops, remediation throughput), never from repeating a manual action.
Basis
direct: operating-state events documented in WorldObject.cs:28-39 ("the status for describing if the object is currently in use (Ex: A workbench that is working on a crafting task)"). external: SAE J3016 / FAA Part 107 as a mature framework for "how much unattended operation is permitted, and what must the operator prove first"; BetterMining's precedent that the community expects automation gated through the skill-point economy.
Rationale
Eco skill trees are mostly stat ladders; a ladder of autonomy grades makes each level-up a story players tell ("my drones don't need babysitting anymore") and lets early-game drones exist without breaking balance — the tedium reduction is itself the progression reward. Gating XP behind automation-built-and-running forces engagement with the mod's actual content from level 1 instead of manual grinding with drones as a late-game afterthought.
Downsides
Uptime-based XP needs anti-idle design (reward closed loops and throughput, not just powered-on time). The XP formula and talent tree are server-side; the client only surfaces state. Interacts with vanilla profession balance — needs playtesting on a real server.
7.

Diegetic control panels — the object is the UI

drone-automation Confidence 85% Complexity: Medium
Description
Adopt as a ground rule: the ModKit exposes no custom UI system, so the physical object is the entire interface. Gauges and progress dials are animator parameters driven by FloatStates (with StateMachineCountdown for real-time countdowns); scan readouts and ore names render through StringStates; physical buttons are multiple SpecificInteractable colliders with distinct interactionTargetNames and mesh-swap press feedback; status is readable across a room via MaterialEvents color tweens. The same pattern gives every processing table a translucent shader fill-gauge, so hopper state is readable at a distance without opening anything.
Basis
direct: StringStates/FloatStates verified at WorldObject.cs:52,55; interactionTargetName "identifies which part of object was interacted with for server-side context" (SpecificInteractable); ButtonStateController mesh-swapping and TweenFloat shader hooks in the WorldObject dossier.
Rationale
This is a hard client constraint most plans discover late and painfully — after sketching control screens that cannot be built. Embracing it up front dictates the dock prefab's design now, keeps every interaction on verified stock surface, and yields a diegetic control-room aesthetic that is more atmospheric than a menu and likely the mod's visual signature.
Downsides
Complex fleet orders (area selection, filters) are awkward as physical buttons — the design must keep commands coarse (mode dials, not text fields). More animator/prefab work per interactive surface than a hypothetical menu would cost.
